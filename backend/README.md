# Running Trips — Backend

FastAPI + PostgreSQL + Redis, per `docs/BACKEND_PLAN.md` at the repo root.
Read that document first — this README is just "how to run it."

## Stack

FastAPI (async), SQLAlchemy 2.0 (async, asyncpg), Alembic, Redis, ARQ
(background jobs), Stripe, Resend, Cloudflare R2 (S3-compatible, via boto3).

## Local development

```bash
cp backend/.env.example backend/.env
# fill in at least: SECRET_KEY (any random string for local dev)
# Stripe/Resend/R2 keys can stay blank locally — those integrations
# no-op or log instead of failing when unconfigured.

docker compose up --build
```

This starts `postgres`, `redis`, the `api` (runs `alembic upgrade head` then
`uvicorn --reload`), and the `worker` (ARQ, background jobs + the
expired-booking-release cron). API docs at `http://localhost:8000/docs`.

## Project layout

```
app/
  core/       config, security (JWT/password hashing), DB dependency,
              locale resolution, rate limiting, exceptions, pagination
  db/         SQLAlchemy declarative base + async session factory
  modules/    one package per domain area — router.py (HTTP), schemas.py
              (Pydantic DTOs), service.py (business logic),
              models.py (SQLAlchemy ORM), repository.py where query-building
              is non-trivial (trips)
  workers/    ARQ task functions + WorkerSettings (background jobs, cron)
alembic/      migrations — see 0001_initial_schema.py for the full schema
```

Each module mixes public, user, and admin routes together (e.g.
`trips/router.py` has both `GET /trips` and `POST /admin/trips`) rather than
splitting admin into a parallel module tree — see BACKEND_PLAN.md §3 for the
reasoning.

## Database migrations

The initial migration (`alembic/versions/0001_initial_schema.py`) is
hand-written raw SQL rather than autogenerated — this sandbox has no network
access to install Alembic/SQLAlchemy to run `--autogenerate` against a live
DB. It **has** been verified: applied and rolled back against a real
PostgreSQL 16 instance, plus a full insert smoke test exercising every
table's FKs, unique constraints, and JSONB defaults (all passed). Once
dependencies are installed wherever you run this, generate all *future*
migrations normally:

```bash
docker compose exec api alembic revision --autogenerate -m "add whatever"
docker compose exec api alembic upgrade head
```

One known cosmetic gap: the hand-written migration uses `BIGSERIAL` for
primary keys, while SQLAlchemy 2.0's own DDL for `BigInteger` +
`autoincrement=True` on Postgres may prefer an `IDENTITY` column. Both behave
identically at runtime; a future `--autogenerate` run may propose a no-op-ish
diff for this — safe to accept or ignore.

## Endpoints added after the initial pass

`GET /admin/auth/me` — added while wiring up the frontend's admin session
check: `GET /users/me` is deliberately role-gated to `role=user` tokens only
(`get_current_user`), so an admin access token can't use it to fetch its own
profile. `admin_auth/router.py` now has its own `/me`, gated by
`get_current_admin`, returning `AdminUserPublic`.

## What's implemented vs. left as a pattern to extend

Fully implemented end-to-end: auth (signup/login/refresh/logout/Google/
verify-email/forgot-reset password), separate admin auth, users + travel
profiles, race categories, trips (public listing with filters/search/
pagination + full admin CRUD including images/inclusions), bookings (with
row-lock capacity enforcement), Stripe payments (create-intent + webhook),
CMS pages/content sections/site settings, newsletter subscribe/unsubscribe,
contact messages, R2 presigned uploads, audit log.

The audit log is wired into a representative set of admin mutations (trip
create/update/delete, booking status change, content page/settings update)
as the pattern — extend `audit_service.record(...)` into the remaining admin
write endpoints (race categories, images, inclusions, newsletter) the same
way as you build out the admin dashboard.

## Testing

`requirements-dev.txt` adds pytest/pytest-asyncio/ruff. No tests are
included yet — add them alongside each module as the frontend starts
exercising the API, using a docker-compose Postgres override for the test DB
rather than mocking the ORM.

## Verification note (this build pass)

This environment's network policy blocks PyPI, so none of the Python
dependencies above could actually be `pip install`-ed here to run the app
live end-to-end. What *was* verified in this sandbox:

- Every `.py` file compiles (`python3 -m py_compile`) — no syntax errors.
- A custom AST-based check across the whole `app/` tree for unused imports
  and undefined names — zero findings.
- The full Alembic migration SQL applied and rolled back cleanly against a
  real local PostgreSQL 16 (installed on this machine), including a data
  smoke test inserting through every table.

Run `docker compose up --build` in an environment with normal internet
access to do a full live run (this is the one step I couldn't complete
myself here) — if anything surfaces there, it'll most likely be in Pydantic
schema/response-model shape rather than the schema or SQL layer, since that
layer is now verified.
